### 4.1 Security decisions (SEC)

| ID | Decision | Status | Criticality | Candidate recommendation (APPROVED) | Rationale | References |
|---|---|---|---|---|---|---|
| SEC-001 | Pairing code format, entropy, and expiry | APPROVED | IMPLEMENTATION-CRITICAL | Six-digit numeric code, 10-minute expiry, one-time use. 5 attempts per 10-minute window per remote address. Code printed to gateway stdout only, never logged. | Numeric codes are easy to read from a terminal, sufficient entropy for the tailnet-protected window, and consistent with the existing `AuthManager` implementation. | THREAT-MODEL §24; PROTOCOL §10, §40; ARCHITECTURE final unresolved list |
| SEC-002 | Cookie lifetime and renewal | APPROVED | IMPLEMENTATION-CRITICAL | Session cookie with 12-hour absolute lifetime. No silent renewal. Reauthentication required after expiry. Rotation on re-pairing. Server-side invalidation on logout or revocation. | Aligns with the phase 1 session model. 12-hour duration matches the documented `Absolute session duration` provisional limit. Renewal is out of scope for phase 1. | THREAT-MODEL §11, §24; PROTOCOL §9, §40; ARCHITECTURE final unresolved list |
| SEC-003 | CSRF mechanism | APPROVED | IMPLEMENTATION-CRITICAL | Double-submit cookie pattern with `SameSite=Strict` cookie and `X-CSRF-Token` header validation. | Already partially implemented in `src/auth.ts`. Extending to WebSocket upgrade validation closes a gap. `SameSite=Strict` prevents cross-origin cookie attachment. | THREAT-MODEL §24; PROTOCOL §9, §40 |
| SEC-004 | Workspace symlink policy | APPROVED | IMPLEMENTATION-CRITICAL | Reject workspace roots that are or contain symlinks to locations outside the configured workspace allowlist. Resolve canonical paths server-side before authorization. | Prevents symlink-based workspace escape. Resolution must happen before the PTY is spawned. | THREAT-MODEL §8.6 T-E-002, §24; ARCHITECTURE final unresolved list |
| SEC-005 | Environment allowlist/denylist | APPROVED | IMPLEMENTATION-CRITICAL | Define a fixed allowlist of permitted environment variables forwarded to the PTY (e.g. `HOME`, `PATH`, `USER`, `TERM`, `LANG`). Deny all others by default. Configured per-launcher. Never expose secrets from the gateway process environment. | Prevents credential leakage. A strict allowlist is safer than a denylist. Common PTY variables must pass through for functional shell behavior. | THREAT-MODEL §24; ARCHITECTURE final unresolved list |
| SEC-006 | Audit retention duration and storage location | APPROVED | NON-CRITICAL | Retain in-memory audit events for the gateway process lifetime. Write to a local JSON-lines file at `~/.pi-pocket-console/audit/` with per-event redaction. No remote export in Phase 1. | In-process audit provides immediate observability. File persistence supports post-restart review. Remote export is deferred. | THREAT-MODEL §24; PROTOCOL §35 |
| SEC-007 | Terminal escape-sequence and external-link policy | APPROVED | IMPLEMENTATION-CRITICAL | Block OSC 52 (clipboard write) by default. Render external URLs as plain text only; no automatic linkification. Sanitize terminal-title escape sequences to printable characters only. Do not execute escape-sequence actions that modify the browser environment. | Prevents terminal escape-sequence abuse for clipboard injection, URL-based attacks, or title-bar information leakage. The user can copy text manually for paste. | THREAT-MODEL §8.4 T-I-004, §24; PROTOCOL §36 |

### 4.2 Lifecycle decisions (LIFE)

| ID | Decision | Status | Criticality | Candidate recommendation (APPROVED) | Rationale | References |
|---|---|---|---|---|---|---|
| LIFE-001 | Lease duration and heartbeat | APPROVED | IMPLEMENTATION-CRITICAL | Lease duration: 5 minutes. Heartbeat interval: 15 seconds. Missed heartbeats: 3 consecutive misses before lease is considered stale. Heartbeat does not extend lease duration; only explicit reacquire or transfer does. | A 5-minute duration keeps the control window short without excessive lease churn. 15-second heartbeat confirms transport liveness without flooding. 3-miss threshold (45s) tolerates brief network hiccups. | PTY-LIFECYCLE §28; PROTOCOL §22, §40; THREAT-MODEL §24; ARCHITECTURE final unresolved list |
| LIFE-002 | Lease behavior during short detach | APPROVED | IMPLEMENTATION-CRITICAL | On transport loss, the lease remains valid for its remaining duration or the reconnect deadline, whichever is shorter. The same device reconnecting within the lease window may resume control without explicit reacquisition if the generation matches. Transfer or explicit reacquisition is required for a different device. | Avoids forcing reacquisition on every brief network blip while keeping the control window tight. The reconnect deadline already bounds the detach period. | PTY-LIFECYCLE §10.3, §28; PROTOCOL §14, §26 |
| LIFE-003 | Idle activity definition | APPROVED | IMPLEMENTATION-CRITICAL | **Resolved by Phase 0 reconciliation (C-07).** Idle timeout resets only on accepted user input or an explicit authorized keep-alive/session action. PTY output, heartbeat, replay, and resize do not reset idle. Absolute expiry never resets. | Already reconciled. Included here for approval tracking. | PTY-LIFECYCLE §9.3, §15.2; PROTOCOL reconciliation section |
| LIFE-004 | Shutdown timeout | APPROVED | NON-CRITICAL | Gateway graceful shutdown: 10-second total deadline. First 5 seconds: send SIGTERM to each PTY. Final 5 seconds: SIGKILL remaining process trees. Abrupt shutdown (process kill) provides no grace period. | Symmetric to the graceful termination window. 10 seconds total gives processes a fair chance to exit while keeping shutdown bounded. | PTY-LIFECYCLE §17, §28 |
| LIFE-005 | Platform process-tree termination | APPROVED | IMPLEMENTATION-CRITICAL | Linux: `kill(-pgid, signal)` by process-group ID with ownership validation. macOS: same strategy, with fallback to `kill(pid, signal)` and child enumeration via `pgrep -P`. Windows: taskkill `/F /T /PID` with tree termination and ownership validation. | Platform-specific implementation is unavoidable. The owned process identity (PID, start time, process-group ID, platform handle) provides anti-reuse evidence before each force operation. | PTY-LIFECYCLE §19, §28; THREAT-MODEL §24; ARCHITECTURE final unresolved list |
| LIFE-006 | Orphan detection | APPROVED | NON-CRITICAL | At gateway startup, scan for processes matching known PTY-launcher patterns. Log any detected orphans as audit events. Do not automatically terminate them; require administrative review. | Start-of-process orphan detection provides visibility without risk of killing the wrong process. Auto-termination of orphans is too aggressive for Phase 1. | PTY-LIFECYCLE §19, §28; THREAT-MODEL §24 |
| LIFE-007 | tmux attach/create lifecycle | APPROVED | NON-CRITICAL | tmux launcher is disabled in Phase 1. The `default-shell` launcher is the only enabled type. tmux attach/create lifecycle decisions are deferred to a later implementation phase. | Phase 1 scope is a single non-persistent shell. tmux adds session-persistence complexity that requires separate design, testing, and acceptance. | PTY-LIFECYCLE §18, §28; PROTOCOL §12 |
| LIFE-008 | Metadata and replay retention after termination | APPROVED | NON-CRITICAL | Retain terminal metadata (session ID, workspace, launcher, timestamps, state, exit code) for the gateway process lifetime. Discard replay buffer immediately on terminal termination. Do not persist terminal output to disk. | Metadata retention supports diagnostics without storing potentially sensitive terminal output. Replay is bounded and transient by design. | PTY-LIFECYCLE §28 |

### 4.3 Protocol decisions (PRO)

| ID | Decision | Status | Criticality | Candidate recommendation (APPROVED) | Rationale | References |
|---|---|---|---|---|---|---|
| PRO-001 | Idempotency retention window | APPROVED | NON-CRITICAL | Retain idempotency keys and results for 60 seconds for terminal creation, termination, lease acquisition, transfer, and release. Reject a reused request ID with different parameters. | 60-second window covers typical retry-after-timeout client behavior. Consistent with the reconnect deadline value. | PROTOCOL §27, §40 |
| PRO-002 | Terminal dimensions | APPROVED | IMPLEMENTATION-CRITICAL | Minimum: 20 cols × 5 rows. Maximum: 500 cols × 200 rows. Default: determined by client viewport measurement at attach time. | Conservative bounds prevent resource exhaustion. Client-measured dimensions keep the terminal responsive to viewport changes. 20×5 minimum supports even narrow phone screens in landscape. | PROTOCOL §29, §30, §40; PTY-LIFECYCLE §9.2 |
| PRO-003 | JSON versus future binary output | APPROVED | NON-CRITICAL | Phase 1: UTF-8 JSON text frames only. Binary WebSocket frames are deferred. If binary framing is introduced later, it must use a new protocol version. | JSON text frames are simpler to validate, debug, and implement for Phase 1. Binary framing with `ArrayBuffer` transfer would improve throughput but requires separate negotiation and testing. | PROTOCOL §4.2, §40 |
| PRO-004 | Close-code finalization | APPROVED | NON-CRITICAL | Adopt the suggested close codes from PROTOCOL §33 as final for protocol version 1. Add two codes: `4007` (idle timeout) and `4008` (absolute expiry). | The suggested codes cover the Phase 1 error surface. The two additions map expiry types to distinct close codes for client UI differentiation. | PROTOCOL §33, §40 |
| PRO-005 | Gateway restart restoration | APPROVED | NON-CRITICAL | Phase 1 does not support gateway restart restoration. On restart, all prior terminal sessions are invalid. No stale sessions are presented as active. Clients receive `TERMINAL_NOT_FOUND` for old session IDs. | Restoration requires persistent session state, replay state, and orphan handling that are out of scope for Phase 1. The architecture document explicitly defers this. | PROTOCOL §40; PTY-LIFECYCLE §17.2; ARCHITECTURE final unresolved list |

### 4.4 Visual and device decisions (VIS)

| ID | Decision | Status | Criticality | Candidate recommendation (APPROVED) | Rationale | References |
|---|---|---|---|---|---|---|
| VIS-001 | Exact Graphite ANSI palette | APPROVED | NON-CRITICAL | Use a 16-color ANSI palette anchored in cool graphite tones. Black (#1a1a1a), white (#e0e0e0). Cyan (#00afaf) distinct from the UI Precision Cyan (#0891b2). Build a color-contrast pass against WCAG 2.1 AA for all foreground/background pairs. | Graphite ANSI is the locked visual direction. Exact values need measurement and contrast validation before release. ANSI cyan and UI cyan must remain visibly distinct per the visual system contract. | VISUAL-SYSTEM §14, §34; IPHONE-ACCEPTANCE §51 |
| VIS-002 | Contrast matrix | APPROVED | NON-CRITICAL | Validate every ANSI foreground/background pair and every UI text/background pair against WCAG 2.1 AA minimum (4.5:1 for normal text, 3:1 for large text). Produce a contrast report before release. | Accessibility requirement from the visual system document. Must be measured, not estimated. | VISUAL-SYSTEM §5.3, §12.3 |
| VIS-003 | Terminal cell geometry | APPROVED | IMPLEMENTATION-CRITICAL | Use xterm.js default cell geometry. Calculate terminal dimensions as `floor(availableWidth / cellWidth) × floor(availableHeight / cellHeight)`. Recalculate only after viewport stabilization (250ms debounce). | xterm.js provides consistent cell measurement. The debounce prevents flickering and wasted resize events during viewport transitions (keyboard open, rotation). | VISUAL-SYSTEM §12, §32; IPHONE-ACCEPTANCE §51 |
| VIS-004 | Viewport stabilization algorithm | APPROVED | IMPLEMENTATION-CRITICAL | Debounce `visualViewport` resize events by 250ms. If a new event arrives within the window, reset the timer. On timeout, recalculate terminal fit and issue one resize. Discard intermediate dimensions. | Prevents resize storms during keyboard open/close and orientation changes. The 250ms value is standard for iOS keyboard transitions. Must be validated on-device. | VISUAL-SYSTEM §12.2, §32; IPHONE-ACCEPTANCE §40, §51 |
| VIS-005 | Responsive breakpoints | APPROVED | NON-CRITICAL | Phase 1: single-column layout for all viewports. Desktop and tablet expand to wider terminal surface but retain the same navigation structure. Optional side navigation at >= 768px width, deferred to a later implementation phase. | Simpler implementation for Phase 1. The visual system authorizes progressive terminal-first expansion for larger screens. Breakpoints can be refined with device testing. | VISUAL-SYSTEM §12.2, §34; ARCHITECTURE final unresolved list |
| VIS-006 | Haptic support and fallback | APPROVED | NON-CRITICAL | Use `navigator.vibrate` for short haptic feedback on destructive confirmation (force termination, session end). Provide a toggle in Settings. Silently fall back if the API is unavailable. Do not vibrate on automatic state changes (reconnect, output arrival, heartbeat). | Haptic feedback reinforces high-consequence actions. Browser vibrate is widely supported. Automatic haptics would be intrusive. | VISUAL-SYSTEM §34; IPHONE-ACCEPTANCE §13, §29 |
| VIS-007 | Supported iOS range | APPROVED | NON-CRITICAL | iOS 17.0+ with Safari WebKit engine. iOS 16.x is tested on a best-effort basis but not a release blocker. Primary device is iPhone 16 Pro running the latest iOS release at development time. | The iPhone 16 Pro is the primary acceptance device. iOS 17 provides the Service Worker, PWA, and WebSocket APIs needed. | VISUAL-SYSTEM §2; IPHONE-ACCEPTANCE §51 |
| VIS-008 | Performance and memory budgets | APPROVED | NON-CRITICAL | Cold-launch to shell visible: target under 3 seconds. Sustained terminal output: maintain 60fps rendering at 80×24 terminal dimensions. Memory: under 150MB for one terminal session including replay buffer after 10 minutes of sustained output. Exact budgets require baseline measurement. | Provisional targets based on mobile-device constraints. Must be validated with on-device profiling. The iPhone Acceptance document explicitly defers exact budgets until baseline measurement. | VISUAL-SYSTEM §34; IPHONE-ACCEPTANCE §41, §42, §51 |
